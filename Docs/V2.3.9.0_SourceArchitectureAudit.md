# V2.3.9.0 源码级架构审计与重构基线报告

## 5. 真实依赖关系图 (Dependency Graph)
当前系统的运行态与诊断态依赖图：

```text
[UI 层]
   │
   ├─ PaletteController (强耦合 WorkspaceController 刷新)
   │
   └─ LocalInspectorPanel
         │ (UI -> Core 的直接调用编排)
         ├─> WorkspaceController (直接读取 Component / Wires 属性)
         ├─> CircuitStateAnalyzer (调用 Analyze() 生成报告基础)
         ├─> CircuitValidationService (依赖其进行 Helper 规则判定)
         └─> IndustrialCircuitRuleAnalyzer / TeachingCheckReportFormatter (部分规则复用)

[运行核心]
   │
   └─ SimulationEngine
         │
         ├─> WorkspaceController (挂载、生命周期和单例查找)
         ├─> RuntimeStateManager (存取元件电流、触点运动状态)
         └─> CircuitStateAnalyzer (每帧核心推导调用 Analyze())

[依赖方式评估]
- 大量通过 `WorkspaceController.Instance` 或直接引用的对象进行交互。
- 缺少抽象接口：`CircuitStateAnalyzer` 直接知道所有的底层 `TerminalConstants` 和特定类型的元件结构（违反依赖倒置）。
- 重复构建拓扑：`CircuitValidationService` 内的众多 Helper 与 `CircuitStateAnalyzer` 各自单独构建图邻接表。
```

## 6. 已有模块化成果审计
- **核心逻辑独立性**：近期新增的 `PowerPotentialValidationHelper`、`TimerControlBypassValidationHelper` 等确实实现了逻辑隔离，但存在大量的拓扑重算现象。
- **模板和实例依赖**：绝大部分 Validator 已经不依赖具体的 `KM1/KT2` 实例名称，但在规则的判断中依然隐式假设了某些组合的存在。例如 `AreThermalRelayOutputsConnectedToMotor` 这种硬编码业务直接嵌在 Inspector 和 Helper 内部。
- **评价**：当前是“把代码搬出去”的初步阶段，未真正解耦。未来可以作为拆分边界，但目前仍有部分冗余扫描。

## 7. 规则通用性源码核查
- **通用性**：诸如 `POWER_POTENTIAL_CONFLICT` 已经能够非常通用地根据 Terminal 的电压值判断；但部分如 `THERMAL_RELAY_CONTROL_BYPASSED` 依然有强烈的三相工业模板倾向。
- **测试入口**：所有的 Helper 实现目前已具备一定的 Editor Test 覆盖（见附录），基本能够做到逻辑拦截，但在包含复杂混合电路时存在一定的误报边界。

## 8. 重复工作与性能热点审计
基于对 `CircuitStateAnalyzer` 和 `CircuitValidationService` 源码的观察：
1. **重复构建拓扑图**：`CircuitStateAnalyzer.AnalyzePass()` 和 Validator 各个子 Helper 都在针对同一批 `Wires` 反复建立局部甚至全局邻接表。
2. **循环中的高频 GetComponent**：`PaletteController.cs` 中过滤切换时重复执行 `GetComponent<Button>` 和 `AddComponent`（行 `413-435` 区间），产生可观的 GC 开销。
3. **大量的中文拼接**：`LocalInspectorPanel` 和 `CircuitStateAnalyzer` 大量利用 `StringBuilder` 逐行拼接长中文字符串，但多数在纯 UI 层面执行，尚可接受。
*结论：目前无 Profiler 支持，不作为 P0 优化项，但重复拓扑图建立应作为长线架构改良的目标。*

## 9. Null 防御分类
目前源码中 `!= null` 的大量出现并非都是合理的保护。
- **A 类 (必须保留)**：`component.gameObject == null` (Unity 销毁检测)。
- **B 类 (必须保留)**：`issue.Component != null` (全局故障有时确实不对应特定元件)。
- **D 类 (掩盖 Bug)**：在 `CircuitStateAnalyzer` 内部对 `WireManager.Wires`、`definition.name` 或 `terminal.id` 频繁判空。此类核心拓扑数据若为空，应尽早（Fail Fast）抛出异常或断言，而不是静默返回，导致未知状态被伪装成正常状态。

## 11. 候选重构切口 (Top 3)

### 第一刀候选：解耦检查助手报告的字符串生成 (InspectorReportFormatter)
- **目标**：将 `LocalInspectorPanel` 和 `CircuitStateAnalyzer` 内部所有拼接中文的 `BuildPathExplanation`、`FormatValidationIssue` 迁移至纯 C# 静态工具类。
- **收益**：立竿见影地削减核心逻辑类近 500 行无业务价值的纯字符串格式化代码；极度安全。
- **回滚方式**：直接还原方法。
- **风险**：低。

### 第二刀候选：抽离拓扑上下文缓存 (CircuitAnalysisContext)
- **目标**：解决 Helper 和 Analyzer 反复重建拓扑的问题，构建一个单次传递的内存快照容器。
- **风险**：中。需要改变 `ValidationService` 的入口参数。

### 第三刀候选：检查流程编排抽离 (InspectorService)
- **目标**：将 `LocalInspectorPanel` 降级为纯粹的 View 层，所有的 `Analyze` 和 `Validate` 调用由不可见的 `Service` 完成，向 UI 暴露 `ViewModel`。
- **风险**：高。牵扯整个 `LocalInspectorPanel` 的核心结构改变。

## 12. 最终建议与禁止事项
- **推荐第一刀**：执行**解耦检查助手报告的字符串生成**（即提取 `InspectorReportFormatter`）。
- **推荐第二刀**：执行**检查流程编排抽离**。
- **推荐验证方式**：生成现有模板的快照（Snapshot）进行 Diff 比对测试。
- **当前绝对不要动的部分**：`CircuitStateAnalyzer.cs` 的状态递归迭代推导（`AnalyzePass` 和 `FindShortestPath`）。在未补充任何自动化基线前，触碰极易引发雪崩。
